# World Cup 2026 Correlations — v1.1 "Make it real & browsable" — Design

**Date:** 2026-06-27
**Status:** Approved
**Builds on:** v1 ([`2026-06-25-worldcup-correlations-design.md`](2026-06-25-worldcup-correlations-design.md))

## Summary

v1 shipped a working correlations app, but two things make it feel empty: it
runs on a 4-team **seed** snapshot (not real data), and nations appear only as
anonymous dots — there is no way to *see* the teams. v1.1 closes both gaps in
one focused increment:

1. **Browse view** — a sortable `/teams` table listing every nation with its
   flag, name, and full stat line.
2. **Polish** — country flag emoji on scatter points (and in the feed/tooltips),
   plus minor formatting consistency.
3. **Real-data enablement** — expand the seeded reference tables to full
   coverage (16 host venues, 48 qualified nations) and extend the football
   parser so a real ingestion run produces *complete* data. The user supplies
   their API-Football key and runs ingestion; this work makes that run pay off.

## Goals

- Let the user actually see and sort the nations, not just hover dots.
- Make a real ingestion run produce a complete snapshot (all teams, all stat
  fields populated), not a partial one.
- Keep every v1 architectural invariant: snapshot-only reads in the app, the
  variable registry as the single source of truth, no API key in the client.

## Non-Goals (v1.1)

- Per-nation detail pages (deferred; the table is the browse surface for now).
- Players / squads / individual stats (out of the data model entirely).
- The all-time historical scope (still v2).
- Live updates, accounts, sharing.

## Decisions (confirmed during brainstorming)

- **Browse view = sortable table** (not a card grid, not detail pages).
- **Flags = emoji**, derived from the country code — fully offline, no image
  hosting, consistent with the snapshot-only model.
- **`passAccuracy` and `cards` become real**: the v1 football parser stubbed
  them to 0; v1.1 parses them from the API-Football statistics payload so the
  table columns and registry variables are meaningful.

## Components & Boundaries

### Browse view (app, snapshot-only)

- **`src/app/teams/page.tsx`** — a client page that loads team rows via
  `rowsForScope("2026-team")` and renders them through `SortableTable`. Linked
  from the existing home and explorer nav. No new data source.
- **`src/components/SortableTable.tsx`** — a self-contained, controlled-ish
  sortable table. Columns are derived from the **variable registry**
  (`variablesForScope("2026-team")`) so labels and number formatting never
  drift from the charts, plus a leading flag+name column. Clicking a header
  toggles sort direction; one column sorted at a time. No external state.
- **`src/lib/flags.ts`** — `flagEmoji(iso3: string): string`. Maps the 3-letter
  ISO code to its 2-letter code, then to the regional-indicator emoji pair.
  Returns a neutral placeholder (🏳️) for unknown codes. Pure and unit-tested.

### Polish (charts)

- `CorrelationCard` scatter points render the nation's flag emoji as a label
  (team scope). Implemented via Recharts' label/custom-label on the `Scatter`,
  reading the point's existing `label` field (already the country/team name) +
  a flag lookup. Falls back cleanly when the label is empty (match scope still
  works). Tooltips show flag + name.
- Number formatting stays sourced from each variable's `format` function — no
  ad-hoc formatting in the table or labels.

### Real-data enablement (ingestion, build-time only)

- **`ingestion/venues.ts`** — expand `VENUES` from the 4 seeded entries to all
  **16 World Cup 2026 host stadiums** with latitude/longitude (used for the
  Open-Meteo weather join). `lookupVenue` is unchanged.
- **`ingestion/countries.ts`** — expand `COUNTRY_ISO3` to cover all **48
  qualified nations**, so `toIso3` resolves every team name from API-Football
  and the World Bank ingestion can fetch each nation's stats.
- **`ingestion/football.ts`** — extend `parsePossession`/stats parsing to also
  read **pass accuracy** and **(yellow+red) cards** from the API-Football
  statistics array, and have `build-snapshot` aggregate them per team (replacing
  the v1 hardcoded 0). The cached-response, free-tier-respectful fetch design is
  unchanged.
- **README runbook** — exact steps: create `.env` with `API_FOOTBALL_KEY`, run
  `ingest:football` → `ingest:worldbank` → `ingest:weather` → `build:snapshot`,
  noting the free-tier limit means football ingestion may span multiple runs
  (cached fixtures are skipped).

## Data flow

Unchanged from v1: ingestion scripts (with the user's key) write raw caches and
build `public/data/{teams,matches,meta}.json`; the app reads only that snapshot.
The browse table and chart labels are new *readers* of the same snapshot — they
add no new fetch path and no new file.

## Error handling

- `flagEmoji` returns 🏳️ for any code it can't map — never throws, never
  blanks a row.
- `SortableTable` renders whatever rows it's given; an empty snapshot yields an
  empty table with headers (no crash), consistent with the charts' "not enough
  data" behavior.
- Ingestion parser additions tolerate missing stat fields (a fixture lacking
  pass-accuracy contributes nothing rather than `NaN`), matching v1's defensive
  parsing.

## Testing

- `flagEmoji`: unit tests — known iso3 → correct emoji, unknown → placeholder.
- `SortableTable`: render rows, click a header, assert row order changes; assert
  columns come from the registry (a registry variable's label appears as a
  header).
- Football parser: extend existing fixture-based tests to assert pass-accuracy
  and cards are parsed from a realistic statistics payload, and that
  `build-snapshot` aggregates them (no longer 0).
- Reference tables: a test asserting `VENUES` has 16 entries with finite
  lat/lon and `COUNTRY_ISO3` covers the 48-nation list (guards against typos in
  the data entry).

## Risks / Open questions

- **Flag emoji rendering** depends on the viewer's OS/font; on platforms
  without flag glyphs they degrade to letter pairs. Acceptable for a fun app.
- **48-nation / 16-venue data entry** is factual and must be correct; the count
  + finiteness tests catch structural errors but not a wrong coordinate. Venue
  coords and the qualified-team list are sourced from public record at build
  time.
- **API-Football statistics shape** for pass accuracy/cards must match the
  parser's expectations; the fixture-based test pins the assumed shape, and a
  real run validates it. If the free tier omits a stat, that field stays empty
  rather than breaking the build.
